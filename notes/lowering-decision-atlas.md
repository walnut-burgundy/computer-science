# Where lowering decisions are made

Status: navigational design note, 2026-10-24. This is an **inspectability contract**, not an implemented optimizer, a measured win, or a claim that a proposed representation is already supported.

## Purpose

The hard part is often not benchmarking a trie against a scanner, or calculating what a memory layout costs. It is discovering **which component made the choice, what facts it used, what other paths exist, how to replace the choice, and how to see whether the replacement survived the remaining lowering stages**.

Automatic lowering is acceptable. Hidden decision ownership is not. No need to preselect one optimal representation for all processors.

For every consequential choice we should be able to answer:

1. **Where:** exact repository, branch/revision, source file, symbol, pass, and emitted artifact.
2. **Who:** semantic language, architecture search, target backend, packager, operating-system/runtime optimizer, or actual hardware?
3. **Why:** input facts, legal alternatives, selection rule, rejected alternatives, and uncertainties.
4. **Change:** the source edit, compiler option, policy input, runtime setting, or replacement implementation that can alter it. Say explicitly when we cannot control it.
5. **Observe:** before/after form, instruction listing, generated bytes, execution trace, exact target and revision, and falsifying tests.

A public source link without the responsible function is a **lead**, not a completed entry in the atlas. A guess about ART behavior is not a machine-level finding.

## Worked question: a fediverse post recognizer

The semantic job: recognize URLs, mentions, hashtags and emoji shortcodes in **changing post text**. Rules and tables can be immutable even though posts, accounts and graph edges are not.

Different decisions occur at different boundaries:

1. **Semantics:** Which character sequences count as mentions or URLs, with which Unicode and escaping rules? Owned by the application/protocol specification, not by DEX.
2. **Algorithm:** Branching scanner, byte-oriented trie, Unicode-aware trie, DFA, classification table or a composition? These are alternatives to record, not an answer fixed by the presence of the word “trie.”
3. **Physical representation:** Encoded DEX constants and bytecode, runtime objects initialized from those constants, a separate APK asset, a memory-mapped region if the loading path supports it, or native ELF read-only data. **Immutable does not imply shared, mapped, zero-allocation, or faster.**
4. **Target lowering:** Which direct-DEX methods, string/type identifiers, instructions, buffers and runtime adapters can currently express the chosen design? Unimplemented features are a gap to report, not a reason to relabel a different implementation as accepted.
5. **Runtime and CPU:** On the actual device, what does ART do with the method, how are objects initialized and reused, and which memory loads, branches and allocations remain? This is observable evidence, not something guaranteed by the DEX source.

For a proposed change, show both `before → after` at the owning transformation and what happened **after** downstream optimizations. Check correctness on tricky input independently of a speed measurement.

## Minimum decision-entry template

| Field | Required record |
| --- | --- |
| Question and semantic invariant | The computation that must not change |
| Owner / stage | Who can choose; who can only observe |
| Exact locator | Repository, revision, path and symbol; an external runtime version when relevant |
| Inputs | Target ABI, runtime, workload, options, profile assumptions, constraints |
| Alternatives | Including simple baseline, rejected alternatives and why |
| Current behavior | What is implemented; proposed or unknown explicitly labeled |
| Change point | Exact edit or control; whether choice can be overridden |
| Output boundary | IR dump, generated DEX, disassembly, memory map, runtime trace, etc. |
| Evidence | Reproducer, independently checked behavior, target/version, measurements and failures |
| Downstream survival | Whether later compiler/runtime stages preserve, replace or erase the choice |

Use these entries as a **discovery index**, not yet a new schema or tool. Prefer linking an existing test and source symbol to building another optimizer.
